Nieuw programmeerconcept

  • Wat is een interface?
  • Wat is een abstract class?
  • implements en abstract methods
  • Polymorphism: hetzelfde contract, ander gedrag
  • Losse verantwoordelijkheden verdelen over classes

Wat bouwen jullie?

  1. Maak een interface Attackable of een interface Attack met een afgesproken methode.
  2. Maak verschillende aanvalsklassen, bijvoorbeeld Tackle, FlameBurst en WaterPulse.
  3. Gebruik een abstracte basisclass voor gedeelde aanvalseigenschappen als dat logisch is.
  4. Laat de BattleEngine een aanval uitvoeren zonder alle specifieke aanvalsklassen te hoeven kennen.
  5. Voeg beurtvolgorde, winnen en verliezen toe.

Acceptatiecriteria

De Product Owner (docent) en het team gebruiken deze criteria om te bepalen of het werk echt klaar is.

  • Er is minimaal één interface die door meerdere classes wordt gebruikt.
  • Er is minimaal één abstracte class met een abstracte method.
  • Minimaal twee verschillende aanvalsklassen gedragen zich verschillend.
  • De BattleEngine gebruikt polymorphism en hoeft niet voor elke aanval een aparte if/else te bevatten.
  • De speler kan een aanval kiezen en de tegenstander reageert.
  • Een battle eindigt correct bij 0 HP.

GitHub: wat moet zichtbaar zijn?

  • Maak voor elke user story en grotere taak een GitHub Issue.
  • Gebruik het sprintlabel sprint-5 en eventueel feature of bug.
  • Zet Issues op het GitHub Projects-bord: Backlog, Ready, In Progress, Review, Done.
  • Werk op een branch met een herkenbare naam, bijvoorbeeld feature/issue-nummer-korte-naam.
  • Open een Pull Request en vraag minimaal één teamgenoot om review.
  • Verwijs in de PR naar het Issue met Closes #nummer.
  • Verplaats de taak pas naar Done als de acceptatiecriteria zijn gecontroleerd.

Definition of Done

  • De code werkt en is getest.
  • De code staat in een Pull Request.
  • Een teamgenoot heeft de code bekeken.
  • De PR is gemerged naar main.
  • De GitHub Issue is bijgewerkt en gesloten.
  • De werking is te demonstreren.
